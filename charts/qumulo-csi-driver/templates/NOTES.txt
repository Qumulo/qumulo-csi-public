Check that both workloads are up:

  kubectl -n {{ .Release.Namespace }} rollout status deploy/{{ include "qumulo-csi-driver.fullname" . }}-controller
  kubectl -n {{ .Release.Namespace }} rollout status ds/{{ include "qumulo-csi-driver.fullname" . }}-node

Ready means the driver process is live. It does NOT mean any Qumulo cluster is
reachable, and it does not mean a token works -- neither the controller nor the
node contacts a cluster to answer a Probe. One controller serves many clusters,
chosen per StorageClass, so there is no single cluster to health-check and the
driver is never told the full set.

Per-cluster reachability and credential failures surface where you can act on
them: as ProvisioningFailed events on the PVC that named the cluster.

  kubectl describe pvc <name>

That is deliberate rather than a gap. An earlier Probe did call the cluster,
against an endpoint needing no authentication, and so reported healthy while
every provision failed with 401 -- a controller that stayed Ready for 36
minutes with a dead token.

{{ if .Values.sidecars.snapshotter.enabled -}}
Snapshots are ENABLED. csi-snapshotter is deployed, and volumes can be
snapshotted and restored from a snapshot.

  Requires the cluster-wide snapshot CRDs and snapshot-controller, which an
  administrator installs once for all CSI drivers:

    kubectl get crd | grep snapshot
    kubectl get pods -A | grep snapshot-controller

  A restore copies file by file, so it is bounded: past 50,000 entries
  (files and directories) or 2 TiB it is refused. A large restore may take several provisioning attempts, during which
  the PVC stays Pending -- raise sidecars.provisioner.timeout if that is slow.
{{ else -}}
Snapshots are NOT enabled. The driver implements the snapshot RPCs and can
restore from a snapshot, but nothing calls them until you set
sidecars.snapshotter.enabled and add a volumeSnapshotClasses entry -- and the
cluster needs the snapshot CRDs first.
{{ end -}}
{{ if .Values.sidecars.csiAddons.enabled -}}
Replication (csi-addons) is ENABLED (supported, opt-in). The csi-addons sidecar is
deployed and the driver serves the replication RPCs. VolumeReplication objects
naming one of this release's VolumeReplicationClasses drive Qumulo directory
replication to the peer array the class names.

  Requires the cluster-wide csi-addons CRDs and controller, which an
  administrator installs once for all CSI drivers:

    kubectl get crd | grep csiaddons
    kubectl get pods -A | grep csi-addons-controller

  Quiesce workloads before a planned promote: a frozen source silently drops
  appends. Known limits: docs/reference/supported-features.md, section 5.
{{ end -}}

Scheduled snapshots are attached by: {{ join ", " $scheduled }}.
The cluster takes them on its own. They are deliberately NOT visible as
VolumeSnapshots, so kubectl cannot delete a scheduled backup by accident.
Always set keep= on the schedule, or the snapshots never expire.

{{- if $domains }}
adDomain is set on: {{ join ", " $domains }}.
Those classes nest their volumes under a per-domain directory. This changes the
LAYOUT only -- it grants and restricts nothing. Per-domain access control needs
Kerberos on the export, which this driver does not configure.

Nothing needs configuring for that: ListVolumes and GetCapacity both derive the
domain directory from the class's own adDomain, so a domain's volumes are
listed and its quota measured without a separate path list to maintain.
{{ end -}}
